Newman (2015) microservices coupling dynamic.

What this model says

Service-architecture has a coupling/cascading tradeoff: more services lower local deploy risk (one service breaking doesn't crash the monolith) but increase inter-service dependency surfaces. If coupling exceeds some threshold, a single service failure cascades.

The SD form tracks Services, Couplings, and Cascades. Couplings are pairwise (n choose 2 service-pairs). Cascades are propagation events from one service's failure to its dependents.

Intuition: One service breaking is fine. One service breaking and bringing down 30 others is a microservice outage.

Success measure (model.y)

Healthy services − 2·Cascading-failures.

Penalty on cascading failures is 2× the bonus for healthy operation.

Conjecture (model.rq)

Coupling threshold breached → cascade dominates.

CONFIRM at default for high-coupling regimes.

Stress-matrix cell

micro is process-conditional — input stress is robust (network size doesn't break the thesis) but the coupling parameter is fragile (perturbing it can drop the verdict to neutral).

The SD model

From models/sd.py:

def micro():
  """Newman [14]: services linear, deps quadratic.
  RQ: high coupling_rate erodes throughput."""
  init = {'Services':[5,1,100], 'Deps':[5,0,500], 'Feat':[0,0,500],
          'coupling_rate':[1.5,0,5], 'svc_growth':[0.5,0,5]}

  def step(dt, t, u, v):
    new_svc  = u.svc_growth
    new_deps = new_svc * u.coupling_rate * (u.Services / 5)
    density  = u.Deps / max(1, u.Services * u.Services)
    fps      = max(0.1, u.Services * (1 - 2 * density))
    v.Services = u.Services + dt * new_svc
    v.Deps     = u.Deps + dt * new_deps
    v.Feat     = u.Feat + dt * fps
    v.coupling_rate, v.svc_growth = u.coupling_rate, u.svc_growth

  def y(out):
    return out[-1][1].Feat

  def rq(bg=None):
    bi = init if bg is None else bg
    return verdict("high coupling_rate erodes throughput",
                   y(run({**bi, 'coupling_rate':[0.5,0,5]}, step)),
                   y(run({**bi, 'coupling_rate':[3.0,0,5]}, step)), 'down')

  return Model(init, step, y, rq, 'coupling_rate')

What we learned

No empirical results. micro is structurally dark on the current 8-project family — the projects available are not microservice deployments.

A future session could clone a microservice-style project + manifest scraper.

Implications

  • Family scope limit: an 8-monolith family can't evaluate a microservice thesis. The framework needs deliberate selection of microservice projects for this lift.
  • Service-topology data is project-specific: unlike git-log + JIRA which are nearly universal, microservice topologies live in deploy-time configs (k8s, Helm) that vary widely.
