Mythical Man-Month (Brooks, 1975) — adding people to a late project makes it later. Lifted on 8 OSS projects.

What this model says

Brooks, F. P. (1975). The Mythical Man-Month: Essays on Software Engineering. Addison-Wesley. Brooks argued, from the OS/360 project, that adding manpower to a late software project makes it later. The system-dynamics encoding tracks two personnel stocks — veteran developers and new hires — with a productivity tax that falls on veterans whenever a new hire joins (training cost + intra-team communication overhead).

Intuition: doubling the team does not double output. Each new hire must be trained, which steals time from a veteran. Then every additional team member adds n·(n−1)/2 communication channels. Below some break-even, the new hires never repay their onboarding cost.

Success measure (model.y)

Net work delivered. y = end.Done − end.Todo

Higher is better. Done is the cumulative task count completed; Todo is the remaining backlog. The difference rewards a team that both ships and finishes.

Conjecture (model.rq)

boost = 10 newcomers at t = 10 hurts y. The model runs twice: once with boost = 0 (no surge hire) and once with boost = 10 (10 newcomers all arriving at step 10). Brooks's claim is the latter run produces less y than the former.

A CONFIRM verdict means the boost demonstrably hurts net delivery. REFUTE means newcomers paradoxically accelerated the project. neutral means the gap is within tolerance.

Why it sits in universal

Running stress(brooks, target='inputs') and stress(brooks, target='params') separately gives CONFIRM in both quadrants of the 2×2 matrix — the thesis survives random perturbation of either inputs OR parameters.

The SD model

From models/sd.py, annotated. Every executable line carries a comment. 

def brooks():
  """Brooks [1]: late hires hurt. RQ: boost=10 newcomers @t=10 hurt y."""

  # ---- init: {key: [default, lo, hi]} ----
  # UPPER-cased keys are STOCKS (state of the world).
  # lower-cased keys are PARAMS (the process under test).
  init = {
    'Vet':         [10,    0, 100],   # veteran devs at t=0
    'New':         [0,     0, 100],   # new hires at t=0
    'Done':        [0,     0, 500],   # cumulative completed tasks
    'Todo':        [500,   0, 500],   # remaining backlog
    'boost':       [0,     0, 100],   # *** ctrl *** sudden hire surge at t=10
    'comm_coef':   [0.005, 0, 0.05],  # comm-overhead coef on Vet pairs
    'train_coef':  [0.2,   0, 1],     # training cost per New, paid by Vet
    'prod_rate':   [5,     0.1, 20],  # baseline productivity per Vet
    'mature_rate': [0.1,   0, 1]      # rate New transitions to Vet
  }

  # ---- step: one tick of the simulation ----
  def step(dt, t, u, v):
    # Communication overhead: n*(n-1)/2 pairs * coef
    comm  = u.Vet * (u.Vet - 1) / 2 * u.comm_coef
    # Training drain: each New takes train_coef of a Vet's time
    train = u.New * u.train_coef
    # Net production: Vet hours not lost to comm or training
    prod  = u.Vet * (1 - comm - train) * u.prod_rate
    # Backlog drains down; floor at 0 to prevent overshoot
    v.Todo = u.Todo - dt * max(0, prod)
    # Delivered work grows; floor at 0
    v.Done = u.Done + dt * max(0, prod)
    # New stock decays as it matures; boost adds 10 newcomers at t=10
    v.New  = u.New - dt * u.mature_rate * u.New + (u.boost if t == 10 else 0)
    # Vet stock grows by maturation flow
    v.Vet  = u.Vet + dt * u.mature_rate * u.New
    # Params carry forward unchanged (no parameter drift in this run)
    for p in ('boost','comm_coef','train_coef','prod_rate','mature_rate'):
      setattr(v, p, getattr(u, p))

  # ---- y: success measure ----
  def y(out):
    end = out[-1][1]                  # final state
    return end.Done - end.Todo        # net delivered work

  # ---- rq: the falsifiable conjecture ----
  def rq(bg=None):
    bi = init if bg is None else bg   # baseline init, or a calibrated bg
    return verdict(
      "boost=10 hurts net progress",
      y(run({**bi, 'boost':[0,  0,100]}, step)),   # baseline: no surge
      y(run({**bi, 'boost':[10, 0,100]}, step)),   # perturbed: 10-newcomer surge
      'down'                                       # thesis says y goes DOWN
    )

  # Wrap as a Model namedtuple: (init, step, y, rq, ctrl)
  return Model(init, step, y, rq, 'boost')
design choice The ctrl variable is boost. During the stress() sweep, boost is the one variable that is never randomly perturbed — it is what we are testing.

Data-lift recipe

The lift produces a calibrated value of brooks_tax — the empirical velocity drop veterans take after a late hire joins — from a project's git history alone. No JIRA, no mbox, no proprietary tools.

Full notebook: lifts/lift_brooks.Rmd (kaiaulu vignette style, knits to HTML, branchable into kaiaulu as a PR). Below: the core chunks. 

# lifts/lift_brooks.Rmd — core chunks

library(kaiaulu); library(data.table); library(magrittr); library(stringi)
source("functions.R")
seed <- 1; set.seed(seed)

tool <- parse_config("../tools.yml")        # perceval, scc, refminer, ...
conf <- parse_config("../conf/helix.yml")   # project paths + filters

# ---- 1. parse the gitlog via kaiaulu's Perceval wrapper ----
project_git <- parse_gitlog(
  get_tool_project("perceval", tool),
  get_git_repo_path(conf)
) %>%
  filter_by_file_extension(get_file_extensions(conf), "file_pathname") %>%
  filter_by_filepath_substring(get_substring_filepath(conf), "file_pathname")

# Perceval emits "Tue Jun 21 18:56:46 2011 -0700"; parse to POSIXct
project_git$author_datetimetz <- as.POSIXct(
  project_git$author_datetimetz,
  format = "%a %b %d %H:%M:%S %Y %z", tz = "UTC"
)

# ---- 2. merge developer aliases via identity_match ----
# kaiaulu's identity_match folds "Foo " + "Foo "
# into one identity_id, so downstream cohort math is per-human not
# per-email.
project_log <- list(git_log = project_git)
project_log <- identity_match(
  project_log,
  c("author_name_email"),
  assign_identity_function = assign_exact_identity,
  use_name_only = FALSE,
  label = "identity_id"
)
project_git <- project_log$git_log

# ---- 3. detect late-hire events ----
# A "late hire" = developer whose first commit is >= 365 days after
# the project's first commit. (lifts/functions.R)
late_hires <- detect_late_hires(project_git, min_project_age_days = 365)

# ---- 4. compute pre/post veteran velocity per hire ----
# For each late hire, count veteran commits in symmetric 90-day windows.
window_days <- 90
vc <- compute_velocity_changes(project_git, late_hires, window_days)
vc[, brooks_tax := (pre_velocity - post_velocity) / pre_velocity]

# ---- 5. write calibrated value to outputs/ for the SD framework ----
fwrite(data.table(
  project           = "helix",
  brooks_tax_median = median(vc$brooks_tax, na.rm = TRUE),
  brooks_tax_mean   = mean(vc$brooks_tax,   na.rm = TRUE),
  n_hires           = nrow(vc),
  window_days       = window_days,
  seed              = seed
), "../outputs/lift_brooks_helix.csv")

Helper functions (lifts/functions.R)

# detect_late_hires: first-commit at least N days after project start
detect_late_hires <- function(project_git, min_project_age_days = 365) {
  id_col <- if ("identity_id" %in% names(project_git)) "identity_id"
            else "author_name_email"
  first_commits <- project_git[, .(first_commit_at = min(author_datetimetz)),
                                by = id_col]
  project_start <- min(project_git$author_datetimetz)
  first_commits[, days_after_project_start :=
    as.numeric(difftime(first_commit_at, project_start, units = "days"))]
  first_commits[days_after_project_start >= min_project_age_days]
}

# compute_velocity_changes: pre/post commit rate of veterans per hire
compute_velocity_changes <- function(project_git, late_hires,
                                     window_days = 90) {
  id_col <- if ("identity_id" %in% names(late_hires)) "identity_id"
            else "author_name_email"
  rbindlist(lapply(seq_len(nrow(late_hires)), function(i) {
    hire_id   <- late_hires[i, get(id_col)]
    hire_at   <- late_hires[i, first_commit_at]
    win_start <- hire_at - as.difftime(window_days, units = "days")
    win_end   <- hire_at + as.difftime(window_days, units = "days")
    veterans  <- project_git[author_datetimetz < hire_at, unique(get(id_col))]
    pre_n  <- project_git[get(id_col) %in% veterans &
                          author_datetimetz >= win_start &
                          author_datetimetz <  hire_at, uniqueN(commit_hash)]
    post_n <- project_git[get(id_col) %in% veterans &
                          author_datetimetz >  hire_at &
                          author_datetimetz <= win_end, uniqueN(commit_hash)]
    data.table(id = hire_id, hire_at = hire_at,
               pre_velocity  = pre_n  / window_days,
               post_velocity = post_n / window_days)
  }))
}

What we learned from this model

Brooks effect varies 11× across 8 OSS projects

Running the brooks lift on Apache Helix, junit5, Ambari, kaiaulu, airflow, openssl, tomcat, and camel gives a wide spread of median brooks_tax:

projectbrooks_tax_mediann_hireslanguagenote
kaiaulu −1.1346 R small sample, noisy
camel −0.1445 java small sample, noisy
Ambari +0.029 126 java weakest positive
tomcat +0.055 50 java
Helix +0.113 65 java headline lift target
openssl +0.146 1019 c
junit5 +0.222 169 java
airflow +0.311 1285 pythonstrongest positive

Among projects with n_hires ≥ 50 (5 of 8 cases), all five show a positive Brooks tax — new hires do slow veterans — but the magnitude varies 11× from Ambari's 3% to airflow's 31%. Language doesn't predict effect size; Java has both the bottom (Ambari) and a near-top (junit5). The two negative-sign projects (kaiaulu, camel) have < 7 hires each — statistical noise, not falsification.

Calibrated rq() on Helix

Plugging Helix's brooks_tax_median = 0.113 back into sd.py:brooks() via scripts/calibrate.py: default gap was −147.5 (strong CONFIRM); calibrated gap unchanged because brooks_tax is a derived output, not a direct input to the init dict. The model's comm_coef and train_coef are what drive its predicted tax; lifting them directly is open future work.

Implication for the paper

  • Universal direction, variable magnitude: Brooks holds in sign on 5/5 high-power projects, but the size of the effect is project-specific. Avoid claiming a universal magnitude.
  • n_hires is a power gate: any project with < 30 late-hire events should be reported as inconclusive rather than as evidence either direction.
  • Mechanism leak: the lift gives a net velocity drop, but conflates training cost (linear in New) with communication overhead (quadratic in Vet). Decomposing these empirically requires multi-snapshot identity-match + team-graph data — future work.
